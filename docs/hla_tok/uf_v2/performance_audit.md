# 性能口径与 D0 热点

统一端到端计时从已准备好的 CUDA RGB 开始，包括一次完整 40 Mbps 最大族生成、物理前缀截取、独立 Base 熵解码和状态提交、接收增强 rANS 和最后一次原生 RGB 显示。排除输入盘读、质量指标、网络、对照拷贝。每段先四帧 warmup，再从独立 I 完整回放。正式表含 3 轮、每轮 174 帧，以总帧数除总耗时汇总 FPS，P95 在全部帧上汇总。应用端到端同时保留 I/P、每轮分布、encoder/decoder、Base 可用时刻和 PyTorch 峰值分配。按需生成单列。

历史 174 帧 D0 的 5 Mbps 端到端均值约 150 ms，P95 249.39 ms。H100 局部剖析的四个稳态 P 帧均值约 117 ms。带 record_function 插桩的另一组四帧中，最大族的量化、排名、熵编码和封装合计约 128 ms，其中 E0 分段 rANS 约 85 ms，分组与成本评分约 21 ms，量化和复制约 7 ms。每帧约 3,052 次 C++ 编段和 270 次 C++ 解段调用。显示调用约 4 ms。用历史同步显示均值 5.95 ms 做 Amdahl 估计，即使删除整个显示开销，剩余端到端均值仍约 144 ms。删除第二个完整 decoder 只能解决小部分延迟。

原生代理通过 CUDA Graph 封装。Kineto 导出的 kernel、H2D/D2H、CUDA 同步和分配事件可见范围标记在 `profiling/cuda_activities.json`。原生 Proxy 图内部、工作线程和 GPU 活动可能不可见，未将 CUDA 与嵌套 CPU 时间相加。不能从这些数据精确独立分摊官方 temporal context、Hyperprior 和其共享熵段的 wall time。

优化保留 E0 字节并直接批量写线。接收侧以组分配工作线程，组内保持粗细依赖。Anchor-Fast 去掉完整预览解码，P 由编码端已算出的 Base feature 调用原生重建头取得同值预览。D1 使用现有 CUDA Proxy 作为 Base，轻量增强及重建读出使用 PyTorch FP16 CUDA。首轮串行批处理 40 Mbps 为 18.4 FPS，原生解析和原生并排分段后，早期 34 帧 P95 仍受两次 I 帧影响。正式样本包含三段真实视频和每段的全部 I/P。

最后一轮将原生段批次改到 512，按值数和完整段数选择 4 或 8 个 worker。两个真实 P 访问单元的全增强接收中位耗时从 7.19 和 7.29 ms 降至 3.52 和 3.60 ms，恢复整数 SHA-256 完全相等。实际 Full-max 的 E1 在 40 Mbps 从 P95 33.60 ms 改善到 30.47 ms。额外的整数画布计时用独立的插桩构建和真实逐记录输入。在常规性能实验中使用原生无插桩构建。
