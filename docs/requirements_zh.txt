二、不可妥协的架构约束
1. 原生支持 1920×1080 RGB 输入/输出，正确处理填充、色彩空间及裁剪。允许中间使用低分辨率 Latent，但不能把低分辨率超分图冒充原生高分辨率编码。
2. 时间因果：编码 t 帧只能使用 x_t 和 t-1 及以前已解码的参考状态；不得使用未来帧、双向视频 Attention 或整段未来序列。
3. 保留 AdapTok 的 Learned Latent Queries、统一有序 1D 离散表示、VQ、前缀 Masking、质量 Scorer 和内容自适应分配思想。每帧只有一份由 EncodeOnce 产生的最大长度 Token 序列，任意较短预算必须直接取其前缀，绝不能随预算重新编码或重新排序。
4. 同一帧类型的所有 Token 预算使用同一套 Prefix-conditioned Decoder 参数。禁止设计独立的 Base Decoder、Enhancement Decoder 或独立高分辨率残差压缩器。
5. 允许定义固定的最小参考前缀 K_ref 来更新因果状态，但它是统一 1D 序列的前缀，不是另一个基础 Tokenizer。所有增强 Token 只影响显示输出，不允许改变已经提交的历史状态。
6. 真实渐进传输：已经发送的完整 Token Packet 不变，只追加后续 Packet；接收端不必重新获取旧 Token，可以逐次获得更高预算的 1080p 重建。
7. 不能把 Token 数乘以 log2(codebook_size) 当作最终压缩码率。必须构建真实熵编码码流，统计全部有效字节、包头、侧信息、I/P 帧和传输开销。
8. 不以训练阶段的模拟 Mask 代替实际编码器/解码器，也不能以只运行网络 forward 得到的 FPS 宣称真实编解码性能。
9. 不使用与主架构等价的旧实现、隐式 fallback 或重复兼容路径掩盖失败。原生上游可独立保留为实验对照。

三、模型结构
输入 x_t：[B,3,H,W]，H/W 支持 1080p。DCVC-UF LD 经 pixel_unshuffle(x,8) 和 stride-2 降采样产生约 [B,128,H_pad/16,W_pad/16] 的 y_t；历史的 ref_feature/memory/ctx 必须通过明确的状态接口访问。

实现：
A. CausalLDBackboneAdapter
- expose encode_latent(x_t, frozen_context)、decode_latent(y_hat, frozen_context)、begin_frame(state)、commit_base_state(feature)。
- 在一帧开始时只计算一次时序 context；增强前缀重建必须复用被冻结的同一 context，不得反复执行会更新 memory 的 apply_feature_adaptor。
- P 帧基本骨干使用官方 LD Encoder、Decoder 和 ReconHead。
- I 帧使用 DMCI 骨干及独立输入输出 Adapter，保持其码流前缀与所有预算共享 Decoder 的性质。可以共享 VQ 码本和通用模块，但不强求 I/P 共享所有骨干权重。
- 适配官方权重量化与 q_encoder、q_decoder 等参数。禁止将教师原始帧特征当作新编解码器的解码端参考。

B. LearnedQueryTokenizer
- 使用可训练的、具有固定顺序的 1D Query Embeddings；不得把 Token 固定绑定到 2D 网格。
- 初始配置 N_max=2048、query_dim=192、heads=6、cross_attention_layers=2。
- 将 DCVC 的低分辨率 y_t 和历史条件投影到统一特征空间。
- 优先使用低成本空间 K/V（例如在 68×120 Latent 上轻量投影，再池化到约 17×30），另设低成本高频特征路径供模型利用；避免在原始 1080p 像素上执行全局 Transformer。
- Learned Queries 通过 Cross-Attention 聚合内容，产生 [B,N_max,d] 的固定有序序列。
- 保证 encode_full(x,state) 与任何预算调用生成的前缀严格一致。训练时完整编码后再选择 Mask；不能先按 K 截断 Query 再运行会改变前面 Token 的网络。
- 实现可扩展 N_max=4096/8192 的配置，不得把 2048 写死在模型形状中。

C. AdapTokVQBottleneck
- 参考 AdapTok 的 Bottleneck、SimpleVectorQuantizer。
- 首选 VQ，初始 codebook_size=8192，token_embedding_dim=16；同时开放 4096、32 维等消融配置。
- 推理使用确定性量化；编码和解码必须严格共享码本索引与版本。
- 保存 Token IDs、Embedding、Mask、VQ loss、codebook usage、perplexity 等诊断。
- 第一版不以 FSQ 取代 VQ；FSQ 仅允许作为后续可选消融。
- 网络传输只包含离散索引及必要侧信息，不允许把发送端连续 latent 偷传给解码端。

D. UnifiedPrefixLatentDecoder
- 将已接收的前 K 个离散 Token 嵌入，使用同一套 Token-to-2D Latent Decoder 重建 DCVC 的 y_hat。
- 初始使用约 17×30 固定解码查询网格，借助 Token Cross-Attention 与轻量卷积恢复到 [B,128,68,120]（I 帧按 DMCI 的对应形状适配）。
- 接入官方 LD Decoder/ReconHead，得到完整 1080p 重建。
- 同一个 Decoder 支持 K=128/256/512/1024/2048 等预算，不能为每个 K 单独训练参数。
- 对未收到的 Token 必须使用正确 Mask，且不能使缺失 Token 参与 attention softmax 或归一化。
- 先实现普通 Cross-Attention 版本作为准确性参考，再实现 prefix-cache 优化版本，真实比较两者的数值误差、LPIPS/PSNR 和延迟。
- 若实现流式 Softmax Cross-Attention 缓存：在固定 Query、逐 Token 独立 K/V 投影前提下，使用数值稳定的 running max、exp sum 和加权值累加，实现对新增 Token 的正确前缀归一化；不得把不归一化的直接求和声称为等价 Softmax。
- 不要宣称缓存 Attention 即完成了完整 LD Decoder 增量执行。第一版允许只缓存 Token-to-Grid 中间状态，按实际显示点重新运行后续 LD Decoder；独立报告重建次数与额外成本。

四、前缀可变长度训练
- 复用 AdapTok 的 Block-wise Tail Masking 思想，但适配逐帧因果块；一帧作为基本因果块，连续视频的不同帧可分配不同 K_t。
- 最大 Token 序列只计算一次，每次训练从 {128,256,512,1024,2048} 中抽取 2~4 个前缀；在扩展配置测试 4096/8192。
- 训练低预算、高预算共享 Decoder，不使用独立质量层。
- 对数尺度采样预算并提高两端极值的采样概率；跟踪每种预算的重建误差，避免模型只优化最高预算。
- 使用 latent teacher 蒸馏、MSE、LPIPS、可选 DISTS、VQ commitment/codebook loss、估计码率与前缀失真单调性惩罚。真实 MSE/PSNR 必须用解码视频计算。
- 单调性只作为软约束；统计实际质量下降比例，不得声称数学上保证任意前缀 PSNR 都单调提高。

五、严格因果参考闭环
- 对每帧定义 ref_tokens=token_ids[:K_ref]。K_ref 可配置，实验测试 128、256、512、1024。
- 发送端使用自己从 ref_tokens 解码的 ref_feature 更新下一帧状态。
- 接收端仅使用相同 ref_tokens 解码得到的 ref_feature 更新状态。
- enhancement_tokens 不得更新 ref_feature、memory、ctx 或任何影响未来帧的状态。
- 对同一帧，begin_frame(state) 得到 frozen_context；多次 decode_prefix 必须复用同一 frozen_context；commit_base_state() 只能调用一次。
- I 帧从空状态独立编码与解码，按基础前缀生成 P 帧初始参考。实现定期 I 帧或明确的 reference reset。
- 要求 state fingerprint、frame_id、reference_id、model_id 的一致性检查。丢失参考包时等待可靠恢复或触发显式重同步，绝不默默继续并造成漂移。
- 连续帧训练不使用未来帧或原始历史作解码端参考；使用重建闭环并进行短序列 BPTT。
- 写测试：同一输入与 reference prefix，改变全部增强预算，下一帧状态必须相同；修改未来视频帧，当前帧 Token 与重建必须不变；跨帧连续测试不能有未察觉的状态漂移。

六、真实可追加码流
实现 ProgressiveEntropyCodec / ProgressivePacketStream：
- 用真实离散 VQ indices 形成可终止熵编码包，初始 packet_tokens=128，可配置 64/256。
- 每个 Packet 包含固定版本格式的 frame_id、frame_type、first_token_index、token_count、block_id、payload_len、model/codebook/entropy_version、必要量化与 shape 元数据、CRC；共用字段尽量放在 FrameHeader 以减少开销。
- 概率模型初版可使用静态或历史条件概率表形成真正的 rANS 编码，随后加入轻量块级条件概率模型。不能以未经压缩的 Token ID、pickle、zlib 封装冒充神经熵模型。
- 概率分布必须只依赖接收端已知的历史、包序号及已完成前缀；块内优先并行概率预测，避免逐 Token 串行自回归成为主要性能瓶颈。
- CDF 必须整数化且收发端确定一致。
- 一次 encode_full 生成所有分包。不同预算共享的前置 Packet 字节完全相同。增加预算只追加后续包；不允许更新旧 FrameHeader 破坏已发送前缀。
- Packet 的编码和解码必须 round-trip；缺包不能错误地拼接为连续前缀；损坏包、错误 model_id、乱序、重复包都有确定的处理。
- 实现 Encoder、Decoder 的真实接口：encode_frame、decode_base、append_packets、decode_prefix、get_display_frame、get_state、reset。
- 实现本机 socket 发送/接收演示，证明已经显示基础重建的帧能够收到后续包并改善图像。先使用可靠顺序传输保证状态正确，后续可加入丢包、截止时间和增强包丢弃模拟。
- 报告 I/P 帧、FrameHeader、PacketHeader、侧信息和 payload 的真实总 bit 数。

七、AdapTok Causal Scorer 与在线 IPAL
- 参考官方 TransformerScorer 和 solve_ilp_min，但不能将原版依赖未来时间块的离线 IPAL 直接用于实时在线编码。
- 训练 CausalScorer 从当前 Token 特征、当前/历史已知状态及预算 K，预测多个前缀的 MSE、LPIPS 或其他失真；保存真实预算质量标注和预测误差。
- 用真实包长 R_t(K)，或仅在编码前决策需要时用已校准的码率预测值，形成可用的 RD 点。
- 实现 OnlineTokenAllocator：在估计带宽、缓冲区、播放截止时间、已编码包长度下，选择帧目标 K_t 与 enhancement 包优先级。
- V1 可以扫描有限预算候选，选择截止时间与带宽约束下预测质量最好的前缀；无需引入复杂 RL。
- 保留原版 IPAL/ILP 作为离线预知全部视频的 oracle 对照，但严禁将其作为在线主算法。
- 至少实现 Fixed-K、Rate-only、Causal Scorer Allocation、Offline Oracle 四类对比。
- Scorer 与传输调度不能修改 token_ids 的值和顺序；只能选择已生成前缀的发送长度。

八、训练阶段
Stage 0：复现原生 DCVC-UF LD 与 DMCI 高分辨率实际码流，保存 checkpoint 版本、FPS、PSNR、码率、显存。确认 CUDA Proxy 与 PyTorch forward 的接口差异。
Stage 1：冻结 LD/DMCI 骨干，只训练 LearnedQueryTokenizer、VQ、UnifiedPrefixLatentDecoder；教师 Latent 必须来自原生可解码量化表示，教师只用于监督，不能泄露到学生解码输入。支持 256/512 crop 加速训练，但必须对完整 1080p 做验证。
Stage 2：连续帧因果训练，使用 base-only reference loop；从 4~8 帧到 16~32 帧，按显存使用 truncated BPTT，验证 I/P 状态同步及长期质量。
Stage 3：训练真正的 Token 熵概率模型和 Causal Scorer，接入真实码流；按真实码率重新校准或微调 Bottleneck。
Stage 4：按需微调 LD Encoder/Decoder 的部分参数；重新跑完整 RD、连续视频和时序评估。不要在质量尚未验证时为了速度盲目量化或削减 Token 表达能力。
Stage 5：性能剖析及可验证优化。PyTorch / torch.compile / CUDA Graph / Flash 或 SDPA attention / fused projections / CUDA entropy kernel 应根据瓶颈选择，并分别报告提升。不能为追求快而破坏前缀一致性、码流兼容或因果状态。

训练实现需包含：YAML 配置、固定 seed、AMP bf16、梯度累积、checkpoint resume、OOM 诊断、独立验证集、完整实验元数据、阶段 loss 与各预算 RD 日志。不能把未执行的训练记成成功。

十、验收测试
1. 输入输出 1920×1080 严格正确，检查尺寸填充、裁剪及色彩格式。
2. 对同一帧和同一前态，K1<K2 时 IDs(K1)==IDs(K2)[:K1]，逐个 Token 完全一致。
3. 最大预算一次编码，任意 Packet 前缀可按合法包边界解码，不允许按不同预算重新编码。
4. 已发送 Packet 在更大预算时逐字节不变。
5. 同一类型帧的所有预算使用相同 Decoder 参数；不同 K 仅改变已收到 Token 前缀。
6. 测试 128/256/512/1024/2048 和扩展预算的真实失真，并统计更多 Token 反而变差的比例。
7. I 与 P 帧均支持真实渐进码流，所有新码流经过 bytes -> entropy decode -> Token IDs -> reconstruction 的路径。
8. 发送端和接收端在连续视频中使用相同参考前缀，参考特征在指定数值容差内一致；不同 enhancement 预算不改变后续参考状态。
9. 修改未来帧不得影响当前 Token/解码；解码端不得访问未来帧、原始真值视频或教师 Latent。
10. 测试乱序、重复、损坏、丢失 enhancement 包以及基础包缺失；不能产生未察觉的参考漂移。
11. Scorer 的预测质量与实际质量分别记录，在线调度不能使用未来帧或真实未来网络带宽。
12. 评估 PSNR、MS-SSIM、LPIPS、DISTS、实际 bpp、kbps、编码延迟、基础前缀解码延迟、后续前缀重建成本、P50/P95、稳态 FPS、峰值显存。
13. 测试全帧编码一次之后，增量追加多个 Token 包的真实成本，区分新增 Attention 更新与完整 LD Decoder 的计算成本。
14. 训练日志和性能报告标明真实 checkpoint、Git commit、GPU、模型版本、数据集、样本数以及是否是真实熵码流。
15. 在保持同等实际码率时对比原生 LD、固定空间 Token Bottleneck 和 Learned Query Bottleneck；不能只比较 Token 数。

十一、基准与实验
测试 1080p，另测试 720p 并可选 4K；推荐 UVG、MCL-JCV 与已有合法视频测试数据。避免训练/测试泄漏。
对比原生 DCVC-UF LD、AdapTok 原生设置（注明分辨率和时间块不同，不能直接作为同条件 RD）、固定空间 Tokenizer 以及本方案。必要时增加标准视频编码器基线。
绘制实际码率-PSNR、码率-LPIPS、码率-DISTS、不同预算重建图、不同帧 Token 分配、吞吐率和逐阶段延迟。
性能目标为 1080p 30 FPS，进一步研究 60 FPS；目标未达到也必须如实记录瓶颈，不能通过省略 entropy encode/decode、发送端本地解码或状态更新来提高所报告 FPS。
